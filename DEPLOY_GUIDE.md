# Deploying her isolated SAMS instance

Everything code-related is done and verified (backend builds clean, frontend builds clean). What's left needs your login session, so it can't be automated — but it's just account-creation clicks + copy-paste. ~15 minutes.

---

## 1. Fill in her real details (2 min)
Open `backend/src/data/supervisor-setup.json` and replace every `REPLACE_...` placeholder with:
- her real department/faculty
- her admin login (this is what she uses for Students + Reports tabs)
- her lecturer login (this is what she uses to run attendance sessions — generate QR codes, mark students present)
- the actual course(s) she teaches

This file only ever creates **her** real accounts — no test/dummy lecturers or students get added to her database.

## 2. New Atlas project + database (3 min)
1. atlas.mongodb.com → top-left project switcher → **New Project** → name it `SAMS-Supervisor`
2. **Build a Database** → **M0 Free** → any region → Create
3. **Database Access** → Add New Database User → username/password (save these)
4. **Network Access** → Add IP → `0.0.0.0/0` (allow from anywhere)
5. **Connect → Drivers** → copy the connection string, replace `<password>` with the real password, add `/samsApp` before the `?` so it matches your db name. This is your `MONGO_URI`.

## 3. Push to GitHub (1 min)
```
git add .
git commit -m "Add admin role, separate deploy config"
git push
```
(Your `.env` is now gitignored — it won't get pushed. Good, since it had live credentials in it before.)

## 4. Deploy on Render via Blueprint (5 min)
1. render.com → **New → Blueprint** → connect your GitHub repo (it'll detect `render.yaml` at the root automatically)
2. It creates two services: `sams-supervisor-backend` and `sams-supervisor-frontend`
3. Before deploying, it'll prompt you for the env vars marked `sync: false`:
   - Backend: `MONGO_URI` (from step 2), `FRONTEND_URL` (leave blank for now, you'll fill after step 5)
   - Frontend: `VITE_API_URL` (leave blank for now), `VITE_SOCKET_URL` (leave blank for now)
   - `JWT_SECRET` is auto-generated by Render — you don't need to touch it
4. Deploy. Wait for both services to go live, note their `.onrender.com` URLs.

## 5. Wire the URLs together (2 min)
- Backend service → Environment → set `FRONTEND_URL` = the frontend's `.onrender.com` URL → save (redeploys)
- Frontend service → Environment → set `VITE_API_URL` = `https://<backend-url>.onrender.com/api`, `VITE_SOCKET_URL` = `https://<backend-url>.onrender.com` → save (redeploys)

## 6. Seed her database (2 min)
Locally, temporarily edit `backend/.env`'s `MONGO_URI` to the new connection string from step 2, then:
```
cd backend
npm run seed:supervisor
```
This creates only her real data: her department, her admin account, her lecturer account, and her course(s). No dummy students or test lecturers touch her database — she'll create students herself through the Admin dashboard. Switch your `.env` back to your original `MONGO_URI` afterward.

## 7. Done
Send her the frontend `.onrender.com` URL with **two logins**:
- **Admin tab** (Admin ID + password from `supervisor-setup.json`) — manage students, view/print reports
- **Lecturer tab** (Lecturer ID + password from the same file) — run actual attendance sessions, generate QR codes

Your original Vercel/your-own-Render deployment is untouched.

---

**Heads up on free tier:** Render's free web services spin down after 15 min idle and take ~30-60s to wake up on the next visit. Fine for occasional admin use; if she's checking it daily it might feel slow on the first load each time. A $7/mo upgrade on just the backend service removes that — no rush, only if it bugs her.
